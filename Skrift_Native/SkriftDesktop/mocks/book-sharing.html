Share a book — the .skriftbook bundle

A book you’ve lived in is more than its audio: 28 hours of on-device transcript, an aligned ePub, real-TOC chapters, your bookmarks. Today none of that can leave the phone except through per-book iCloud sync (your devices only, your iCloud storage, a full re-upload). One portable file fixes all of it — AirDrop it to your iPad, Save to Files as a durable archive, or hand it to someone else running Skrift. Same file, same importer, three ways in.

The format — .skriftbook

A ZIP with a Skrift UTI. ZIPFoundation is already an approved dependency (SPM dep #2, pinned 0.9.20, in the app target for the ePub work) and it streams entry-by-entry off disk — so a 795 MB bundle needs no new dependency, no memory ceiling, and gives real byte progress. Audio is already compressed: store the audio entries .none, deflate the JSON.

The Odyssey.skriftbook          UTI com.skrift.book → public.zip-archive, public.data
├── manifest.json                schema · producer build · the Audiobook record · contents flags
│                                · per-file durations + byte sizes (the match test)
├── audio/Odyssey-01.m4a …       ordered, original filenames  (omitted when audio is off)
├── cover.jpg
├── text/wilson-odyssey.epub     every attached text (multi-text ready)
├── derived/transcript_f0.json … the expensive part: whole-book word timings
├── derived/alignment_f0.json …  ePub ↔ audio alignment (spike 6)
└── reader/bookmarks.json        ONLY in a "my other device" bundle

What the engine has to get right

  • Re-stamp the sidecars on arrival. BookTranscriptStore.signature is "<size>:<mtime>" of the local audio, and mtime changes the moment the file is written on the receiving device — so an un-restamped transcript reads as stale and the book silently looks un-transcribed. AudiobookCloudSync.restampTranscripts already solves exactly this for the CloudKit path: hoist it to one shared re-stamper and have both paths call it, rather than growing a second copy.
  • The match test is duration, not bytes. Two rips of the same audiobook never share a size. The manifest carries file count + per-file durations; a no-audio bundle attaches only when the count matches and every duration is within ±0.5 s. Byte-identical → skip the warning. Mismatch → screen 7, never a silent attach (drifting word times are worse than no transcript).
  • Keep the book id — and merge on collision. Re-importing the same bundle twice must be idempotent, so import is keyed on the manifest’s bookID: present locally → merge (screen 6); absent → new book keeping the id. Free win: the sync mock’s stated limitation — “each device mints its own id at import, so two independently-imported copies can never match for resume-sync” — just dissolves. A bundle-transferred book already shares an id, so opting it into CloudKit sync afterwards works.
  • Merge policy. Derived work (transcript, alignment, chapters, ePub) is additive — take the incoming one when it covers more (coveredUpTo / word count), the existing one otherwise. The reader layer follows the existing LWW rule (modifiedAt) and only when the bundle carries one; a “someone else” bundle has none, so a merge can never move your bookmarks.
  • Local-only fields stay local. epubChapters / detectedChapters are derived from local sidecars and are already stripped from the sync blob by Audiobook.sanitizedForSync(). A bundle is the one channel that legitimately carries the files those derive from — so import writes the files and then re-derives, rather than trusting the manifest’s copy.
  • Tests can’t link ZIPFoundation (“app target ONLY — extensions and test bundles never touch archives”). So the testable surface must be pure: manifest codec, the duration-match verdict, the merge/dedupe decision, the re-stamp. The zip I/O is a thin shell verified on device.

Three ways in, one importer

  • AirDrop / Messages / “Open in Skrift” → CFBundleDocumentTypes entry for com.skrift.book with LSHandlerRank: Owner (we own this type, unlike the Alternate-ranked audio/video entries) → .onOpenURL → AppURLHandler gains a book-bundle branch → the confirm sheet.
  • Files app → the Books + already has a fileImporter; add com.skrift.book to its importTypes and the same sheet appears.
  • Export is a plain ShareLink over the packaged temp file — AirDrop, Save to Files and everything else come free.
  • iPad rides along (one universal app). The Mac is a parking spot, not a destination — book files never sync to the Mac by design (Audiobook.swift:19), so a .skriftbook in iCloud Drive is storage there, not an import.

Why this earns its place next to per-book iCloud sync

  • Sync can’t reach another person. One private database, one iCloud account.
  • Sync costs the user’s iCloud storage and a full upload+download; AirDrop is local, free and fast.
  • The 28 hours are the asset. A whole-book transcribe is hours of ANE time. Carrying just the reading work is ~15 MB and skips all of it — a case sync can’t express at all (it moves the audio or nothing).
  • Durable archive. “Save to Files” makes a book’s derived work survive a phone wipe — the full exportability principle applied to books instead of notes.
  • Honest note, not a gate: putting the audio in a bundle for another person redistributes a purchased audiobook. That’s why “Someone else” offers the audio as a switch you turn on, and why the text-only mode is framed as the neighbourly one. No enforcement in the app.

Open — for sign-off

1. A or B? A (destination + audio switch) is the recommendation: 4 combinations, 2 controls, and the privacy layer can’t be forgotten.
2. Does “Someone else” default the audio switch to off? Proposal: yes — the cheap, neighbourly bundle is one tap, the 782 MB one is deliberate. “My other device” defaults it on.
3. Do quote captures ever travel? Proposal: no, not in v1. They’re notes, they live in the memo store, and they already sync as memos. A bundle stays a book.
