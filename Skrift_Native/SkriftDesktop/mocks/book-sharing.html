Share a book with someone — the .skriftbook bundle

A book you’ve lived in is more than its audio: 28 hours of on-device transcript, an aligned ePub, real-TOC chapters. None of it can leave the phone today. One portable file hands the whole thing to someone else running Skrift — AirDrop, Files, Messages, anything. Your own devices are not the point: per-book iCloud sync already carries audio, cover, position, bookmarks, transcript and alignment sidecars between them (Tuur 2026-07-30 — scope cut to person-to-person only, and the design got much simpler for it).

Scope cut 2026-07-30 (Tuur): “Why share with my own other device? All that is done over cloud sync. Just sharing to others is fine.” Correct — AudiobookCloudSync already carries audio, cover, position, rate, bookmarks, transcript sidecars, attached ePubs and alignment sidecars between your devices. What that cut removes: the destination segmented control, variant B, the whole A-vs-B question, reader/bookmarks.json from the format, and the reader-layer LWW branch in the merge logic. And it retires a claim that was wrong once own-device sharing left: the earlier draft said bundle transfer would give two devices a shared book id and dissolve the “each device mints its own id” limit on resume-sync. That only ever held device-to-your-device. Gone.

The format — .skriftbook

A ZIP with a Skrift UTI. ZIPFoundation is already an approved dependency (SPM dep #2, pinned 0.9.20, in the app target for the ePub work) and it streams entry-by-entry off disk — so a 797 MB bundle needs no new dependency, no memory ceiling, and gives real byte progress. Audio is already compressed: store the audio entries .none, deflate the JSON.

The Odyssey.skriftbook          UTI com.skrift.book → public.zip-archive, public.data
├── manifest.json                schema · producer build · the Audiobook record · contents flags
│                                · per-file durations + byte sizes (the match test)
├── audio/Odyssey-01.m4a …       ordered, original filenames  (omitted when audio is off)
├── cover.jpg
├── text/wilson-odyssey.epub     every attached text (multi-text ready)
├── derived/transcript_f0.json … the expensive part: whole-book word timings
└── derived/alignment_f0.json …  ePub ↔ audio alignment (spike 6)

no reader/ directory — bookmarks and position are never in a bundle, by construction

⚠️ The custom-type gotcha that bites THIS project

Dev and Prod run side by side on the same phone by design (com.skrift.mobile.dev + the inverted icon, its own data container). If both builds export the same com.skrift.book UTI, two installed apps claim ownership of one type and document routing becomes undefined — “Open in Skrift” can hand a test bundle to the prod app, straight across the data-safety line. Make the type config-dependent exactly like the bundle ids: com.skrift.book (Release) / com.skrift.book.dev (Debug), with Dev accepting both so real bundles can still be tested. Same trap as the $(VAR)-in-entitlements lesson: keep the value literal per config, selected by build setting.

The rest of the custom-type downsides are minor and mostly mitigated: a recipient without Skrift sees an opaque file (conforming to public.zip-archive is the mitigation — rename to .zip and it’s a readable folder); no Files thumbnail or preview without a QuickLook thumbnail extension (nice-to-have: draw the cover); some mail/cloud services mangle unknown attachments (AirDrop/Files/Messages are fine); and you own the format forever, which is what the manifest’s schema int is for. Declare it exported (UTExportedTypeDeclarations), never imported — we own it.

What the engine has to get right

  • Re-stamp the sidecars on arrival. BookTranscriptStore.signature is "<size>:<mtime>" of the local audio, and mtime changes the moment the file is written on the receiving device — so an un-restamped transcript reads as stale and the book silently looks un-transcribed. AudiobookCloudSync.restampTranscripts already solves exactly this for the CloudKit path: hoist it to one shared re-stamper and have both paths call it, rather than growing a second copy.
  • The match test is duration, not bytes. Two rips of the same audiobook never share a size. The manifest carries file count + per-file durations; a no-audio bundle attaches only when the count matches and every duration is within ±0.5 s. Byte-identical → skip the warning. Mismatch → screen 7, never a silent attach (drifting word times are worse than no transcript).
  • Keep the book id, merge on collision. Import is keyed on the manifest’s bookID: present locally → merge (screen 6); absent → new book keeping the id. That makes re-importing the same bundle twice idempotent — the reason the policy survives the scope cut — and it makes a Files-archived bundle restore cleanly onto a phone that already has the book. Two people ending up with the same book id is harmless: separate iCloud accounts, separate private databases.
  • Merge can’t touch a reading layer, because no bundle carries one. The LWW branch the earlier draft needed is gone; derived work is simply additive — take the incoming transcript when it covers more (coveredUpTo / word count), keep the existing one otherwise.
  • Local-only fields stay local. epubChapters / detectedChapters are derived from local sidecars and are already stripped from the sync blob by Audiobook.sanitizedForSync(). Import writes the files and re-derives, rather than trusting the manifest’s copy.
  • Tests can’t link ZIPFoundation (“app target ONLY — extensions and test bundles never touch archives”). So the testable surface must be pure: manifest codec, the duration-match verdict, the merge/dedupe decision, the re-stamp. The zip I/O is a thin shell verified on device.

Three ways in, one importer

  • AirDrop / Messages / “Open in Skrift” → CFBundleDocumentTypes entry for the config’s book UTI with LSHandlerRank: Owner (we own this type, unlike the Alternate-ranked audio/video entries) → .onOpenURL → AppURLHandler gains a book-bundle branch → the confirm sheet.
  • Files app → the Books + already has a fileImporter; add the book UTI to its importTypes and the same sheet appears.
  • Export is a plain ShareLink over the packaged temp file.
  • No new app extension needed. .onOpenURL + the document type covers AirDrop, Files and Open-in. A share extension would only add in-place handling without launching the app, in a separate memory-limited process — SkriftShare exists for a different job (audio/URL/PDF capture).
  • iPad rides along (one universal app). The Mac is a parking spot, not a destination — book files never sync to the Mac by design (Audiobook.swift:19).

Why it earns its place

  • Sync cannot reach another person. One private database, one iCloud account. That is now the whole justification, and it’s enough.
  • The 28 hours are the asset. A whole-book transcribe is hours of ANE time. Handing someone just the reading work is ~15 MB, redistributes no audio at all, and saves them all of it.
  • Honest note, not a gate: putting the audio in a bundle for someone else redistributes a purchased audiobook. That’s why the audio is a switch rather than a given, and why the text-only mode is framed as the neighbourly one. No enforcement in the app.
  • Known trade-off of the scope cut: “Save to Files” is no longer a complete backup of a book — the derived work archives, your bookmarks and position don’t. Right call for a share format; worth knowing it isn’t a backup format.

Open — for sign-off

1. Does “Include the audio” default on or off? Proposal: off. The cheap, redistributes-nothing bundle is then one tap and the 782 MB one is deliberate.
2. Do quote captures ever travel? Proposal: no, not in v1. They’re notes, they live in the memo store, and they already sync as memos. A bundle stays a book.
